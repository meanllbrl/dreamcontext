# Whiteboard — boards you and the user draw on together

A whiteboard is an editable Excalidraw canvas that carries **live widgets**: an insight card, a Lab board card, a page (a knowledge entry or a project `.md` / `.pdf` / `.html` file) or task link, a todo list, a markdown note, a sandboxed HTML block, a web embed, an **agent card** (an automation agent you talk to on the board, § Agent cards). The user draws on it in the dashboard (**Whiteboard** in the Workspace rail, alpha): the rail entry opens the default board **"Control Panel"** (slug `control-panel`), and a switcher at the top of the board opens, creates and deletes the others. You read and edit boards with `dreamcontext whiteboard …`. It is the brain's control panel and brainstorming wall: "dünkünü sil, bugününü yaz" is two commands.

**Not to be confused with:**
- a knowledge `.excalidraw.md` diagram under `knowledge/<context>/<title>/`: **read-only** in the dashboard, generated by the `excalidraw` skill from a spec, indexed by recall (→ [knowledge-and-recall.md](knowledge-and-recall.md) § Excalidraw boards). You never edit those with `whiteboard`.
- the Tasks page's saved "board" views (kanban filters). Those are not files and have nothing to do with this.

When the user says *board / whiteboard / control panel / pano* and means a place to put things and come back to, it is a whiteboard.

**A number on a whiteboard is a live widget, never a drawing.** "Put current MRR, this month's revenue, the monthly trend, the split on the control panel" means one `insight` widget per metric, so the board re-reads the Lab cache every time it opens. Never draw the values with the `excalidraw` skill's `kpi()`/`lineChart()`/`donut()`, never write a generator script that bakes them, never hand-write the board: all three freeze today's numbers into shapes. A metric with no insight yet gets one first (`dreamcontext lab create`, offer-and-confirm), then its widget. Open work goes on as `task` widgets or a `todo`. Recipe (0) below.

## Storage and format

```
_dream_context/whiteboards/
├── .gitattributes          ← `* merge=binary`: git never line-splices two copies of a board
├── .gitignore              ← `.locks/` and `*.tmp`
├── .locks/                 ← per-board PID lockfiles (machine-local)
├── .trash/<slug>-<ts>/     ← boards deleted from the dashboard land here
└── <slug>/<slug>.excalidraw.md
```

- The **slug** comes from the name (`create "Günlük"` → `gunluk`): lowercase, `[a-z0-9-]`, at most 64 chars, `board` when nothing survives, `-2`/`-3` on collision. The **name** stays verbatim (Turkish-safe) in the frontmatter. The slugs `default` and `pages` are never handed out (they are API routes), so `create "Default"` → `default-2`.
- **The default board** is `control-panel` ("Control Panel"). The dashboard creates it the first time the rail opens it (`GET /api/whiteboards/default`, under the board lock, so it is made once); `list` marks it `(default)` (`"isDefault": true` in `--json`). It cannot be deleted from the dashboard (the API answers 409): clear it instead. Put the user's standing widgets here unless they name another board. A `create "Control Panel"` on a vault that already has it gets `control-panel-2`, like any collision.
- The file is an **Obsidian Excalidraw board**: frontmatter (`name`, `description`, `dreamcontext-whiteboard: 1`, `tags: [excalidraw]`, `excalidraw-plugin: parsed`), a `## Text Elements` list (live text plus widget titles), then `## Drawing` with a **plain** ```` ```json ```` fence. It opens in Obsidian; widgets there show as empty embed frames.
- It is git-tracked, so team brain sync carries it. In `full-repo` sync two machines' edits merge **per element** (a dedicated merge handler), never by lines.
- **Never hand-edit the file.** Every write goes through the CLI or the dashboard, which lock, merge and write atomically. The serializer is byte-deterministic, so a no-op edit leaves the file untouched.
- **Refused, never overwritten:** a board whose drawing block is missing or does not parse, and a board **Obsidian saved compressed** (`compressed-json`). Run *"Decompress current Excalidraw file"* in Obsidian first. `list` shows such a board as `does not parse: <reason>`; every mutation exits non-zero.
- **No images in Phase 1.** An `image` element is refused by the CLI, the server and `draw`; the canvas refuses pasted or dropped images with a visible message.

## The ten widget kinds

A widget is an Excalidraw `embeddable` element with `link: "dreamcontext://<kind>/<id>"` and its payload in `customData.dc = {v: 1, kind, …}`.

| Kind | Payload | Add with |
|---|---|---|
| `insight` | `ref` = Lab insight slug (`lab/insights/<ref>.md`) | `add <slug> insight --ref mrr` |
| `knowledge` (a **page**) | `ref` = knowledge path without `.md` (`knowledge/<ref>.md`), **or** a project-relative `.md` / `.pdf` / `.html` / `.htm` path | `add <slug> knowledge --ref features/whiteboards` or `--ref docs/spec.pdf` |
| `task` | `ref` = task slug (`state/<ref>.md`) | `add <slug> task --ref <task-slug>` |
| `todo` | `items: [{id, text, done}]` | `add <slug> todo --title "Today" --item "…" --item "…"` |
| `note` | `markdown` (rendered sanitized) | `add <slug> note --text "…"` or `--file note.md` |
| `html` | `html` (sandboxed block, see below) | `add <slug> html --file block.html` |
| `web` | `url` (https only) | `add <slug> web --url https://…` |
| `wiki` | `title` + `sections: [{id, title, pages: [{ref, label?}]}]`, the card's own list of pages (see § The wiki card) | `add <slug> wiki --title "Handbook"` |
| `lab-card` | `ref` = `<board>/<card-id>`, one card of a Lab board (`lab/boards/<board>.md`), drawn exactly as Lab draws it (see § Lab cards and funnels) | `add <slug> lab-card --ref growth/c-signups` |
| `agent` | `ref` = automation agent slug (`automations/<ref>.md`), `link` = `dreamcontext://agent/<ref>`: the agent's card, with its conversation and a composer (see § Agent cards) | `add <slug> agent --ref daily-brief` |

Every kind also takes `--title`, `--tag <tag>`, `--at x,y` (top-left), `--size` and `--color`.

### Sizes and the grid

Widgets are sized like Apple's widgets, on a grid of **180px cells with 16px gaps** (`customData.dc.size`):

| Size | Cells | Box (w×h) | Default for |
|---|---|---|---|
| `s` | 1×1 | 180×180 | `knowledge`, `task` |
| `m` | 2×1 | 376×180 | `insight`, `todo`, `note` |
| `l` | 2×2 | 376×376 | `html`, `web`, `wiki`, `agent` |
| `xl` | 4×2 | 768×376 | `lab-card` |

- `--size s|m|l|xl` sets `dc.size` and the box. Without `--size` a widget gets its kind's default and records it. The widget adapts to its size in the dashboard: an `s` insight shows just the number, `l` and up draw the chart; a bigger todo shows more items. The user can also pick a size on the widget, or drag a handle (it snaps to the nearest size).
- `--size w,h` (back-compat) keeps an exact free-form box and leaves `dc.size` unset; the dashboard then shows the **nearest** preset, and `show` reports that nearest size. Prefer the presets.
- **Placement without `--at`:** the widget lands on the grid pitch (196px = cell + gap), in the first grid row, from the top of the board's content down, where it fits to the right of what is already in that row within eight cells (1552px); otherwise it goes below all content at the left. It never overlaps a live element and keeps at least a 16px gap. With `--at`, use multiples of 196 to stay on the grid.

- A `ref` that does not exist yet is a **warning, not a failure**: the widget renders "not found" until the entity appears. The exception is `agent`: its `--ref` must name an existing agent (`dreamcontext automations list`), because an agent never appears on its own.
- Validation on every write: a `lab-card` ref is exactly `<board-slug>/<card-id>` (both kebab-case); an insight or task `ref` matches `^[a-z0-9][a-z0-9-/]{0,200}$` with no `..` segment; a page (`knowledge`) ref is either such a slug or a project-relative path ending in `.md`/`.pdf`/`.html`/`.htm` (no leading `/` or `~`, no `\`, `:`, empty, `.` or `..` segment); a tag matches `^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$`; a todo holds at most 500 items; a text payload is at most 1M chars.
- **Colour.** `--color grey|blue|red|yellow|green|pink|purple|cyan` tints a card (`customData.dc.color`): the hue mixed into the card's surface and border, text unchanged, in both themes. `update --color none` clears it. The user picks the same colours from the button beside S/M/L/XL. Colour groups cards by meaning (a red row of alarms, a green row of revenue), not decoration.
- **Header.** A card with a title shows the title as its heading and no kind label; a card without one names its kind. So give every metric card a `--title` that says what it is ("Ad spend", not "Insight").
- **Placement.** A dragged card snaps to the 196px grid OR to a nearby card's edge (aligned with it, or one 16px gap beside or under it), whichever is nearer, so cards resized shorter than a cell still sit close. `--at` places exactly where you say; keep the 16px gap yourself.
- **Tags** group elements for `remove --tag`. A widget keeps its tag in `customData.dc.tag`; a plain drawn element (a shape or text imported with `draw --tag`) keeps it in `customData.dcTag`. `show` reports both as `tag`.

## Reading a board

```bash
dreamcontext whiteboard list [--json]              # every board: name, slug, element count, (default)
dreamcontext whiteboard show <slug> --json         # every live element
dreamcontext whiteboard show <slug> <id> --full    # one element, payload untruncated
```

`show --json` returns `{slug, name, description, elements: [...], wikis: [...], agents: [...]}`. Each element has `id`, `type`, `bbox {x,y,w,h}` and, where present, `text` (text elements), `tag`, and for widgets `kind`, `size` (`s|m|l|xl`: `dc.size`, or the nearest preset for a free-form box), `ref`, `title`, `items`, `url`, `markdown`, `html`, and a wiki card's `sections`. `wikis` lists every wiki card as `{id, title, size, sections}`. `agents` lists every agent card as `{id, slug, title, home, missing}`: `home: true` when the agent's manifest names this board as its home, `missing: true` when the agent no longer exists. Deleted elements (tombstones) are never listed.

- **What the user ticked**: a todo item the user checked on the canvas reads back as `"done": true`. This is how an agent sees the user's progress. Nothing else needs to be asked.
- `markdown` and `html` are cut to 500 chars with `"truncated": true`; fetch one in full with `show <slug> <id> --full`.
- Moves the user made show up as a changed `bbox`.

## Editing

```bash
dreamcontext whiteboard update <slug> <id> --title "…" --text "…" --url https://… --ref <slug> \
  --item "append this" --check 2 --uncheck <item-id> --at x,y --size s|m|l|xl --color blue|none
dreamcontext whiteboard rename <slug> "New name"       # display name only; the slug stays
dreamcontext whiteboard remove <slug> <id>…          # or: remove <slug> --tag <tag>
dreamcontext whiteboard draw <slug> --file x.excalidraw.md [--at x,y] [--tag t]
```

- `--check` / `--uncheck` take a **1-based position** or an item id, and repeat.
- `update --text` on a plain text element replaces its text.
- `update --size s|m|l|xl` resizes a widget to a preset (sets `dc.size`, width and height, bumps the version). `--size w,h` resizes any element freely and clears a widget's `dc.size`.
- `remove` writes tombstones and prints the **removed group's bbox** (`bbox x,y,w,h`; `--json` → `{removed, bbox}`, `bbox: null` when nothing matched). Text bound inside a removed container goes with it.

## The wiki card

A `wiki` widget is a card holding its **own list of pages**: ordered sections, each holding ordered pages. A board may hold several wiki cards; each keeps its list in its own payload (`customData.dc.sections`), so the list moves, merges (per element, the higher version wins) and syncs with its card. In the dashboard a small card (S/M) is the list and a page opens in the side panel; a large card (L/XL) shows the list with the page read inside the card. A page ref is the same as a page widget's: a knowledge slug or a project-relative `.md` / `.pdf` / `.html` path.

```bash
dreamcontext whiteboard add <slug> wiki --title "Handbook"                         # an empty card, size l
dreamcontext whiteboard nav list <slug> [--card <id>] [--json]                     # sections + pages, 0-based positions
dreamcontext whiteboard nav add <slug> --section "Getting started"                 # a new section
dreamcontext whiteboard nav add <slug> --section <id|title> --page architecture/overview [--label "Overview"] [--at 0]
dreamcontext whiteboard nav add <slug> --section "Specs" --page docs/spec.pdf     # a missing section is created
dreamcontext whiteboard nav move <slug> --section <id|title> --to 0                # reorder a section
dreamcontext whiteboard nav move <slug> --section <id|title> --page <ref|#n> --to 2 [--to-section <id|title>]
dreamcontext whiteboard nav remove <slug> --section <id|title> [--page <ref|#n>]   # a page, or the whole section
```

- `--card <widget-id>` picks the card. Leave it out when the board has exactly one wiki card; with several, the command refuses and lists their ids and titles; with none, it says to `add <slug> wiki --title …` first. `show <slug> --json` lists every card's id under `wikis`.
- A section is found by its id first, then by title (case-insensitive); two sections with the same title need the id. A page is found by its ref or its 0-based position (`#2`). `--to` is 0-based, clamped, and negative counts from the end.
- A page that does not exist yet warns, never fails. A ref with `..`, an absolute path, or another extension is refused. At most 100 sections per card and 500 pages per section.
- Every edit is a normal widget write: it bumps the card's version under the board lock, so an open dashboard picks it up and a stale browser copy cannot undo it. A deleted card's tombstone drops its list.

## Lab cards, funnels and the date window

**A funnel insight is drawn as a funnel, never a table.** An `insight` widget whose insight renders `funnel` shows, at `s`/`m`, the users at the top step and the share that reached the last one over a mini lane (one bar per step, its height the share of the top; `m` writes each step's conversion from the previous one under it; every bar's tooltip has users, % of previous and % of top). At `l`/`xl` it draws the **Lab funnel explorer** itself, the card `lab board add-card --preset funnel-explorer` makes: breakdown chips over Daily / Benchmark / Flow / Steps / one Segments tab per dimension, opened on Steps, with a full-screen button. Chips and tabs work on the board; the pick is the widget's own and is not saved. The insight must be synced (an unsynced one shows the plain card).

**Any Lab board card goes on a board as a `lab-card`.** `whiteboard add <slug> lab-card --ref <board>/<card-id>` (card ids: `dreamcontext lab board show <board>`) draws that card through Lab's own engine: the same blocks, selection, tabs, app pages and full screen. The board keeps only the ref, so an edit to the card in Lab shows on the whiteboard. A board or card that is gone says so on the widget. The canvas palette offers it as **Lab card…**. Prefer this to a derived insight that re-states a card's numbers.

**The date window is on the card.** Every `insight` and `lab-card` widget whose insight has a window prints the window its data covers in the header ("6 Tem – 4 Eki", from the cache, not from the last request), and once the widget is active the chip opens Lab's range control (the insight's declared presets, quick windows, a custom from/to). The window belongs to the **insight**, as everywhere in Lab: applying writes the insight's range tweak and re-syncs, so two widgets of one insight always show the same window. From the CLI: `dreamcontext lab tweak <insight> range last_28_days`, then `lab sync <insight>`.

**Keep related insights on one window with `tweaks_from`.** An insight derived from another (a stat card next to its funnel) declares `tweaks_from: <source-slug>` in its manifest frontmatter. A window change on any member of the group (the source or a follower, from a widget, a Lab card, the detail panel or `lab tweak`) is written to all of them, and the dashboard re-syncs the others after the one you touched. One hop only: followers name the source, never each other.

## Agent cards: an agent that lives on the board

An `agent` widget is an ordinary automation agent ([automations.md](automations.md)) drawn as a card you talk to. The card never owns the agent: removing the card leaves the agent, and a card whose agent was removed shows a notice and stays.

**Home or attached.** An agent is **at home** on a board when its manifest says `whiteboard: <board>`: create it with `dreamcontext automations create <slug> --title "…" --whiteboard <board>` (or the canvas palette's **New agent**), then put its card there with `dreamcontext whiteboard add <board> agent --ref <slug>`. The field is approval-hashed, the approval records which board was approved, it cannot be combined with an output directory, and nothing re-homes an agent later. Any other agent's card on a board is **attached**: it keeps its normal permissions and only borrows the board as context. `show --json` tells them apart (`agents[].home`).

**A home-board agent acts only on its board.** Every spawn of one (a run, an account-switch continue, a reply, an answered question, a card conversation) runs under Claude Code's own permission rules instead of `bypassPermissions`: `--permission-mode dontAsk --setting-sources project` and an exact allowlist. Anything not on the list is denied.
- **Reads:** `Read`, `Glob`, `Grep`, `LS`, `WebFetch`, `WebSearch`, and the read verbs `snapshot`, `memory recall`, `tasks list`, `knowledge index`, `lab list|show`, `whiteboard list|show|nav list`, `automations list|show|thread|pattern|flow`.
- **Writes:** `whiteboard add|update|remove|draw|nav add|nav remove|nav move <its board>`, `automations post|learn|propose <itself>`, and files only under `automations/output/<itself>/` and its scratch folder `$DREAMCONTEXT_AGENT_SCRATCH`. Nothing else: no shell redirect into a file, no `Agent`, `Task` or `Workflow`, no skills, no MCP.
- **Never read:** `~/.ssh`, `~/.aws`, `~/.claude`, `~/.claude.json`, `~/.dreamcontext`, `~/.config/gh`, `~/.config/gcloud`, `~/.docker`, `~/.gnupg`, `~/.kube`, `~/.azure`, `~/.npmrc`, `~/.netrc`, `~/.git-credentials`, `~/.pypirc`, and anywhere any `.env*`, `*.pem`, `*.key`, `id_rsa*` or `id_ed25519*`.
- **A second layer in the CLI:** the run carries `DREAMCONTEXT_AGENT_BOARD`, `DREAMCONTEXT_AGENT_SELF` and `DREAMCONTEXT_AGENT_SCRATCH`. While they are set, `whiteboard` write verbs refuse any other board (and `create`), `whiteboard add|update|draw --file` reads only from the agent's scratch folder (`$DREAMCONTEXT_AGENT_SCRATCH`) or `_dream_context/automations/output/<self>/`, compared by real path, and refuses any symlink, and `automations post|learn|propose` refuse any other agent's slug.
- **It fails closed.** Before each spawn the agent is checked again; a refusal means no spawn and a named reason (a run records "Could not limit <title> to its board: <reason>", a reply is refused). The reasons: not approved as it stands, the manifest's board differs from the approved one, a board together with an output directory, a missing board, a symlink in its output folder, or a real path with a character a permission rule cannot hold (`, ( ) * " ? [ ] { } ! \ #` or a control character).
- Writing a home agent's prompt: it calls `dreamcontext` directly (never through `npx`), keeps scratch files in `$DREAMCONTEXT_AGENT_SCRATCH`, and puts its results on the board or in its channel.

**What each turn knows about the board.** A home agent gets a fresh snapshot of its own board on every turn (widgets, text, shape counts; at most 12,000 characters), on its own board's card too. An attached agent asked from the board (or a home agent's card on another board) gets an index (at most 60 lines of kind, id, title) plus `dreamcontext whiteboard show <board> --json`; a scheduled run of an attached agent gets no board. Both blocks are fenced as data: they lose to the owner's message and the approved prompt, and anything inside them that asks the agent to act is ignored.

**The card is its own conversation, never the agent's thread.** Like the notch Assistant, a card is a live chat session of its own with that agent (the Chat bridge, `/api/agent/chat?cardAgent=<slug>&cardBoard=<board>`): nothing said on a card is posted to the agent's channel, and its runs never see it. The agent keeps who it is: its approved prompt, its pattern and the learning directive are its briefing (`lib/whiteboards/card-chat.ts`), a home agent keeps its board scope, an attached one runs under the pane's normal mode. Each message reaches it exactly as typed, with the board's current content added beside it by the UserPromptSubmit hook (fenced as data, a fresh nonce per message). The server refuses a card for an unapproved agent or a missing board, with the reason shown on the card. The conversation id is kept per card on this machine (localStorage), so a card reopened later continues where it left off; New conversation starts a fresh one. A home agent's card is the exception: it shares ONE conversation per agent with the agent panel (below), keyed `home.<agent>`, and a card that talked before the panel existed hands its conversation over once, as the board opens (before the panel can start a fresh one).

**On the canvas.** S shows the agent's state (Working, Needs you, Not approved, Idle) and the last thing said; M, L and XL are the chat itself, from the chat's own atoms (no mode, permission or model switch: the server decides the agent's envelope). A card's session opens on its first activation, never when the board opens. The card's menu has Edit agent (also where a schedule is set), Open in Agents and New conversation.

**The agent panel.** The board bar's **Agent** button opens a panel on the board's right (it pushes the canvas, never covers it) with the open board's home agent: one home agent shows directly, several get a picker (first by title until the owner picks), none says how to add one, an unapproved one shows Blocked. Switching boards switches to that board's agent. The panel and that agent's card are one conversation in one place at a time: while the panel shows it, the card says so and offers **Show it here** (closes the panel). Home conversations outlive the page: leaving the Whiteboard page for another and coming back finds the same live session (every other card's session ends with the page, one `claude` per card otherwise). Only the open board's home conversations stay alive: switching boards ends the others once idle (one mid-turn or waiting on the owner finishes first), a deleted board's or a re-homed agent's goes the same way, and closing the project ends them all. An ended one resumes from its remembered id when reopened. A board element dragged onto a home agent's card lands in that shared conversation's composer.

**The page remembers where you were**, per project on this machine (localStorage, never the synced board file): the last open board (reopened if it still exists and no link names another), each board's scroll and zoom (restored instead of fitting to content), and whether the agent panel was open. The corner agent dock and Chat button are hidden on the Whiteboard page so they never sit on cards; a floating dock over an open overlay stays.

**Drag to ask.** Drag up to 4 elements onto an M or bigger card: they go back where they were and become reference chips in the card's composer (`dcref:wb/<board>/<id>`). The hook expands each chip into the element in full (at most 4,000 characters each), so the agent reads exactly what the owner pointed at; the owner's own bubble shows a Board element chip in place of the token.

**From the Assistant:** `dreamcontext assistant agent <vault> "<text>" --board <board>` reaches that board's home agent (none: refused with the boards that have one; several: ambiguous), `--slug <slug>` reaches any agent. It is gated like `assistant send`.

## Recipes

### (0) A control panel of metrics: one insight widget per number

```bash
dreamcontext lab list                                # which metrics are already tracked
dreamcontext lab create mrr-split --title "MRR split" # only for a metric with no insight yet
dreamcontext whiteboard add control-panel insight --ref mrr --title "MRR" --size s --tag panel
dreamcontext whiteboard add control-panel insight --ref revenue-monthly --title "Revenue by month" --size l --tag panel
dreamcontext whiteboard add control-panel insight --ref mrr-split --size l --tag panel
dreamcontext whiteboard add control-panel task --ref <urgent-task-slug> --tag panel
```

Size picks the view: `s` is the number alone, `m` adds the change and a sparkline, `l`/`xl` draw the chart. The insight's own `render` (`line`, `bar`, `pie`, `funnel`, …) decides the chart, so a split wants a `pie` insight, not a drawn donut. A heading or a short explanation is a `note`. Rebuilding the panel is `remove control-panel --tag panel` and the same adds.

### (a) The daily board: yesterday out, today in, same place

```bash
BOX=$(dreamcontext whiteboard remove gunluk --tag daily --json | node -e 'let s="";process.stdin.on("data",d=>s+=d).on("end",()=>{const b=JSON.parse(s).bbox;console.log(b?`${b.x},${b.y}`:"")})')
AT=${BOX:+--at $BOX}
dreamcontext whiteboard add gunluk note --title "$(date +%F)" --file today.md --tag daily $AT
```

Reusing the printed bbox's `x,y` puts today's items where yesterday's were, instead of drifting right every day. On the first run nothing is tagged, `bbox` is `null`, and `add` auto-places. Place a second widget of the same run one grid step from the first (`x + 392` beside an `m`, i.e. two 196px pitches) rather than letting it auto-place elsewhere.

### (b) Today's todo list, and reading back what the user did

```bash
dreamcontext whiteboard add gunluk todo --title "Bugün" --item "Review PR #42" --item "Ship docs" --tag daily --json
# → {"id": "<todo-id>", …}. Later (next session, or the next automation run):
dreamcontext whiteboard show gunluk <todo-id> --json   # items[].done === true is what the user ticked
dreamcontext whiteboard update gunluk <todo-id> --check 2 --item "Follow up with design"
```

Carry the unticked items into tomorrow's list; report the ticked ones as done (and tick the matching task criteria if they map to one).

### (c) Importing a drawing from the excalidraw skill

Only for a drawing with no live data in it (a flow, a sketch, a wireframe); a metric is recipe (0). Build the diagram with the `excalidraw` skill's builder as usual (it writes an `.excalidraw.md` or a scene `.json`), then:

```bash
dreamcontext whiteboard draw gunluk --file /tmp/funnel.excalidraw.md --at 0,400 --tag funnel
```

`draw` re-ids every element and keeps bindings, containers, groups, frames and element links consistent, offsets the group so its top-left lands at `--at` (default: right of existing content), and prints the imported ids and bbox. An image element in the source refuses the whole import. Remove the drawing later with `remove --tag funnel`.

## HTML blocks and web embeds: what runs

**HTML block** (`html`): board HTML can come from a shared repo, so it runs like chat's sandbox **minus the input bridge**.
- `<iframe sandbox="allow-scripts">` under a strict CSP: **no network** (no fetch, no external scripts, styles, fonts or images), no same-origin access, no top navigation. A block that tries to navigate (`location.href = …`) is torn down and replaced with "This block tried to open a web page".
- **No `dc-tabs` behaviour.** The kit CSS is there, but the kit's tab switching is not. Want tabs? Write your own inline `<script>`.
- **No input bridge and no data bridge.** A block cannot send keys or clicks to the board, and cannot read brain data. Put the data in the HTML when you write it (re-write the block to refresh it). The frame reports its height only (capped at 4000px).

**Web embed** (`web`): the URL must be `https:`, carry no username/password, and not point at the dashboard's own origin (checked at write time and at render time).
- **Click-to-load.** The widget shows the host (Unicode and punycode side by side) and a **Load** button. "Trust <host> on this machine" auto-loads that host on every board from then on; the list is per machine (browser storage), never synced.
- The frame gets `allow=""`, no popups, no top navigation; "Open in browser" goes through the normal external-open path.

## Concurrency and merge, in two sentences

Every writer (CLI, dashboard save, git-sync merge) merges **per element** under a lockfile: the higher `version` wins, ties go to Excalidraw's `versionNonce` rule, and deletions are kept as tombstones so a stale browser cannot resurrect what the CLI removed. An open board polls every 2 seconds and folds a CLI edit in within about 3 seconds without dropping the user's unsaved strokes; if the user keeps dragging an element you just removed, their newer version wins and it comes back.
