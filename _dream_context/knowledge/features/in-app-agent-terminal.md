## Why

Developers using the dreamcontext desktop app need to run Claude Code interactively without leaving the app or opening a separate terminal window. The in-app Agent terminal embeds a full Claude Code TUI session directly in the Sleepy/Agent screen — full session parity (slash menu, skills, sub-agents, reasoning effort, real permission prompts) because it IS the client. In-app prerequisite detection and installation (node-pty, claude CLI) eliminate setup friction so the feature works out of the box.

As of 0.22 the TUI is no longer what you land in. The native **Chat** screen — the same engine rendered as app UI — is the default surface for every user, and the embedded terminal is kept as **Terminal (legacy)** behind Settings → Agents → "Agent screen". The flip includes a one-time migration: every pre-0.22 `agent-ui.json` carries `chatView:false` from the old opt-in default, so that value is only honoured once the blob has been stamped `screenMigrated` — which is what moves existing users onto Chat without overriding anyone who deliberately picks the terminal afterwards.

- [x] As a developer, I can navigate away from the Agent tab and return without losing my Claude Code session.
- [x] As a developer, I can opt into bypassing Claude Code's permission prompts so I can let it operate autonomously (with a standing warning shown while armed).

- [x] As a developer, I can read Claude Code's output clearly in both light and dark themes without eyestrain or same-luminance-on-same-luminance blocks.
- [x] As a developer, I can install missing prerequisites (Claude CLI, node-pty) from within the app with one click so I never need to open a terminal just to unblock the Agent screen.
- [x] As a developer, I can access the agent terminal from any page via a global bottom-right FAB so I never need to navigate to a dedicated Sleepy page.
- [x] As a developer, I can see per-pane tab bars so it is always unambiguous which tab controls which pane.

- **[2026-08-01] Never write `scrollTop` while the scroller is still in motion — the drag lesson generalizes to every animator.** Owner re-reported the transcript flicker/teleport (loading old entries, and shedding them, "breaks my scroll") after the 07-28 hold shipped and its matrix held 7/7. The matrix could not have caught it: the shipping WKWebView animates scrolling OUT OF PROCESS, and trackpad momentum — which Playwright cannot emit — keeps deriving the offset from its own decay curve for a second-plus after the fingers lift, exactly as the scrollbar thumb derives it during a drag (the one mode we COULD reproduce, which showed the cascade frame by frame: write undone → "near the ceiling" again → reveal again). So any `scrollTop` the pane writes mid-momentum is either overwritten (cascade) or kills the glide dead (stutter). Fix is a discipline, not a patch: every window mutation paid for by a `scrollTop` write waits for QUIET — the auto-reveal arms a `SCROLL_SETTLE_MS` (150ms) timer that every input event re-arms, and the pinned window's snap-to-tail is gated `pinned && settled` at the render-time normalization, so momentum-into-the-bottom can't unmount 200 revealed rows mid-flight. Three load-bearing details: (1) quiet is tracked off INPUT events only (wheel/touch/scroll-keys + drag flag), never scroll events — the pin's own re-asserts dispatch those constantly while a turn streams, and counting them would freeze the memory valve forever; (2) 150ms sits between a trackpad's intra-gesture gaps (~16ms — a glide never counts as settled; macOS momentum keeps emitting wheel events its whole decay) and deliberate notch pacing (~200ms+ — paced scrolling still reveals between notches, keeping the continuous feel); (3) the pinned trim gained `TRIM_SLACK` (20) hysteresis — one-row-per-frame unmounts shrank `scrollHeight` on every token (clamp + re-pin + scrollbar wobble), and a chunk shed every 20 items is the same bounded memory at a twentieth of the churn. Runtime-proved by the new `npm run verify:chat-scroll` (22 checks incl. fold-row held to the pixel across a settled reveal and no snap while wheel events arrive). Apply to any surface that both animates scroll natively and writes offsets programmatically: defer the write to quiet, or don't make it.
- **[2026-07-27] "Auto" is the CLI's `auto` mode, never `acceptEdits`. They are different modes and only one of them matches the promise on the card.** CLI 2.1.220 accepts six permission modes (`acceptEdits | auto | bypassPermissions | manual | dontAsk | plan`). Chat spawned `acceptEdits`, the terminal had already moved to `auto`, and nothing in the UI could tell them apart, so the composer's Auto card said "edits auto-approved, risky commands still ask" while the session asked about essentially every command. Measured on 2.1.220 in a real stream-json session with `--permission-prompt-tool stdio`, same four commands each time: under `acceptEdits`, `npm --version` and a `curl` both raised a `can_use_tool` prompt and only the file-writing command went through unasked; under `auto`, all four ran with no prompt. Fixed in `permissionModeFor` (`bypass ? 'bypassPermissions' : 'auto'`), which every chat spawn AND the live `set_permission_mode` switch read from, so the flag and the switch can never disagree. The live switch takes `auto` too (verified: acked `{subtype:'success', response:{mode:'auto'}}` and re-emitted `system:init` with `permissionMode: auto`), so a running conversation flips without a respawn. Rule for any future permission work: the mode string is a product claim, so verify it against the running CLI rather than against the mode list you remember, and keep the chat and terminal spawns reading one shared mapping.
- **[2026-07-27] Closing a webview is not free — never destroy a window in the same tick as the action that asked for it.** Issue #234: submitting a pinned checklist whose item list had grown scrollable (expanded note + file rows) segfaulted the WHOLE app — `EXC_BAD_ACCESS` in `WebCore::ScrollingTree::takePendingScrollUpdates()`, reached from `RemoteLayerTreeDrawingAreaProxy::didRefreshDisplay()`, with no app frames in the stack: WebKit servicing a display-link refresh against a webview already being torn down. The non-scrollable checklist submitted cleanly, which is what points at the scrolling tree rather than at the submit. `ChecklistWindow` called `getCurrentWindow().close()` in the same tick as the successful submit, while the scroller still had updates in flight. The fix is sequencing in two halves that only work together: (1) flip to a phase that **unmounts the scrollable content**, removing the scrolling node from the layer tree; (2) close two animation frames after that render, so a display-link cycle services the update first — with a timeout fallback, because an occluded window throttles `requestAnimationFrame` and a checklist that never closes would be worse than the crash. The ✕ button takes the same road: the trigger is closing a scrolled window, and the title bar can do that just as easily as Submit. Honest limitation: the fault is inside WebKit's own teardown, so this removes the documented trigger rather than proving the race can't be lost. Apply to any future window this app closes from its own UI.
- **[2026-07-27] "The renderer crashed" is what an uncaught React render throw looks like from the outside — and every peripheral panel needs a boundary.** Issue #236 reported Cmd+clicking a directory chip as a WebContent process crash, and the host-side evidence genuinely pointed there: main process alive, no `.ips` report, view blank. It was none of that. `GET /api/agent/file` answers a folder with `{type:'dir', entries}`, the file panel modelled only `{type:'text'|'markdown', content}`, and `content.split('\n')` on `undefined` threw during render — with no boundary between that panel and the transcript, React unmounted the tree and the conversation went blank. Two rules. (1) **Model every arm of a response you already ship.** The dir arm was not a new feature request; the route had answered folders with listings since it was written, and the client quietly assumed it wouldn't. A client that narrows a server's union without a default arm is one payload away from this. (2) **A surface that sits OVER a live conversation gets its own error boundary.** The panel is peripheral; the transcript behind it may hold the only copy of an hour's work. `PanelBoundary` catches, names the error, and keeps the close button — a stuck scrim is its own dead end. The app-level boundary was too coarse for this: it exists, and the failure still read as "the app broke". Apply to any future overlay/panel/drill-in over the chat.

- **[2026-07-27] An attachment is a PATH or it is nothing — a preview is not a channel.** Chat's composer accepted a pasted image by building an object URL and showing a thumbnail, then dropped it from the outgoing message (`attachments.filter(a => a.kind !== 'image')`), because when the beta shipped there was no way to move raw bytes over a text-only protocol. The result was the worst possible shape of a missing feature: the UI confirmed the attachment, the user asked about the picture, and the agent answered about nothing — "copy paste atınca okumadı, ama add file diyince okudu" (Anıl, 07-27). The upload channel had existed since the drag-drop work (`POST /api/agent/drop` writes into the gitignored vault temp dir and returns an absolute path); paste simply never used it. Two rules follow, and they generalize past this surface. (1) **Never render an affordance whose backing channel doesn't exist.** If bytes can't be delivered, the chip has to say so (`couldn't attach — not sent`) — a chip that looks identical either way is a lie the user only discovers from the agent's answer. (2) **An async attachment makes submit wait, not drop.** ⌘V then ⏎ is one gesture, and the upload is a loopback write of a few milliseconds; `submit` awaits in-flight jobs (behind a single-flight guard) and `commit` re-reads draft/busy/quote from a live ref, because a closure captured before the await is stale by definition. Corollary for the transcript side: a path is what the AGENT needs and the last thing the SENDER should see, so the bubble draws the trailing attachment paths as media and shows only the typed words — while `item.text` stays the real message, since copy/quote/rewind are about what was sent, not what was displayed.

- **[2026-07-26] A card that ASKS should page horizontally; only a card that TELLS may stack.** A 2-question AskUserQuestion card rendered every question stacked vertically, which put the second question's options below the fold and the Submit button below THAT — the card read as a wall of text to scroll rather than as something being asked, and the user could not see the thing they were meant to act on without scrolling past the thing they had already acted on. Owner call: multi-question survey cards page, one question per page. Two implementation rules are load-bearing and easy to get wrong. (1) **Measure the active page, don't let the track size the card.** A flex track holding every question makes the container as tall as its TALLEST page, so every shorter question sits under dead space — the viewport's height is written from the active page's own `offsetHeight`, and it is OBSERVED (not measured once per page change) because the page can grow underneath you when the "Other" textarea opens or gets dragged. The track must be `align-items: flex-start` or the observer chases itself: a stretched page's height would depend on the height just written to the viewport. (2) **An off-screen page is `inert`, not merely translated away.** Its option buttons are still real buttons — without `inert` they stay in the tab order and the a11y tree, so a keyboard user tabs into a question they cannot see. Two UX rules follow from the same principle that paging hides state: the answered/current dots and the `n left` readout exist because "how much is left" stopped being visible as scroll length, and `n left` is a BUTTON only when the gap is off screen (a button that navigates to the page you are already on is a dead click). The primary action flips to `Submit →` on completeness, never on position — otherwise someone who answered by jumping around has to walk to the last page to send. Single-question cards render exactly as before: the pager is chrome for a problem they don't have.
- **[2026-07-25] React compares dangerouslySetInnerHTML by object identity — memoize to preserve out-of-React DOM decorations.** `MarkdownPreview` passed a fresh `{__html: body}` object on every render. React compares `dangerouslySetInnerHTML` by identity, so it rewrote `innerHTML` on EVERY commit even when the markdown hadn't changed by one character. The rewrite destroyed every chat-local decoration (a media reference turned into a `<video>`, a path into a clickable chip, a code block into one with a Copy bar), and nothing re-ran to restore it because the effects' deps `[body, item.done]` were untouched. Fixed by memoizing the object (same text → same object identity → React skips the rewrite); the three decoration hooks now also run every render (marker-guarded, so an already-decorated subtree is a no-op), making the decoration self-healing instead of one-shot. Apply this pattern to any future React component that uses `dangerouslySetInnerHTML` and also applies post-render DOM decorations — memoize the prop, make decorators idempotent.
- **[2026-07-25] A shrinking scroller under a pinned view fires no scroll event — re-measure and re-pin on the next frame.** When docked furniture BELOW a transcript scroller grows (shells tray, auto-growing composer), the scroller shrinks under a view already at its maximum — `scrollTop` stays perfectly valid, the maximum moves away from it, and **no scroll event is dispatched** because nothing scrolled (verified in Chromium against real CSS: 186px tray growth left 174px of transcript silently below the fold while the view believed it was pinned). Fix: `scrollToBottom()` re-measures on the next `requestAnimationFrame` (`isAtBottom` extracted, shared with `nextStickToBottom` so one definition) and re-pins if the bottom moved. Also: the `ResizeObserver` no longer re-subscribes on `syncRail`'s identity (which follows `subAgentCardEl`, so a fan-out card mounting tore the observer down and back up) — that teardown window was the one gap where a height change went unseen. Apply this re-measure-a-frame-later pattern to any future stick-to-bottom surface where content can shrink on its own (live logs, auto-collapsing cards, resizing furniture).
- **[2026-07-25] TTL-eviction wake scheduled from the soonest expiry, never derived from `now`.** `BackgroundShellsTray` wakes once at `nextExpiryAt` (the soonest row to expire) rather than polling. `nextExpiryAt` is deliberately never derived from `now`, because the component schedules its next render FROM it — a `now`-derived wake is a render loop. The value is computed from the shells' own `endedAt` stamps, not the current clock. Apply this pattern to any future TTL-driven eviction: schedule the next wake from the data's own timestamps, not the scheduling instant.
- **[2026-07-25] Docked chrome below a scroller must be size-capped, three ways.** The background-shells tray sits outside the scroller on purpose (a background shell outlives its turn), which means every row it holds is height the transcript does not get and cannot scroll past. Bounded three ways: (1) a finished row is evicted `FINISHED_SHELL_TTL_MS` (2 min) after it ends (`isShellVisible`, applied inside `summarizeBackgroundShells`); (2) the rows list scrolls inside `max-height: min(240px, 32vh)` instead of growing the tray; (3) the tray collapses to its header once the last shell exits (`useGroupCollapse`). Apply these three caps (TTL eviction, internal scrolling, collapse-when-idle) to any future docked furniture that holds unbounded rows outside a scroller (live feeds, notification strips, debug panels).
- **[2026-07-25] Excalidraw pinch zoom is module-level state — per-instance registration required.** `@excalidraw/excalidraw` 0.18 drives WebKit pinch gestures from module-level state shared by every `<Excalidraw>` instance on the page, so one board's pinch was zooming ALL boards to the same level. `excalidrawPinch.ts` `registerPinchTarget()` / `unregisterPinchTarget()` per-instance fix: each canvas calls register after `excalidrawAPI` mounts (lazy, because the API arrives in an effect) and unregister on unmount. The API is read lazily, never assumed present.
- **[2026-07-25] Composer drag sets a FLOOR, never a fixed height.** Both drag and auto-grow want to own the composer's height, so one must be subordinate. Rule: `applied = min(ceiling, max(autoGrown, draggedFloor))`. Auto-grow is what the CONTENT needs (may always push up to ceiling). Drag is what the USER asked for (a minimum the content may exceed but never undercut — a deliberately tall box doesn't collapse under you when you send or delete a line). Neither may pass paneHeight/2 (the ceiling drag has always enforced — auto-grow can't reach a size drag is forbidden). Visible consequence: dragging DOWN stops at the current draft's natural height (won't hide typed text). With a short draft (common case), the full drag range is available because the natural height IS the two-line minimum. After send the draft is empty, so autoGrown collapses to 2-line min and box returns to max(min, draggedFloor) — i.e. to two lines for anyone who never touched the handle, to their chosen size for anyone who did. Drag is a standing choice, not leftover state.
- **[2026-07-25] Per-instance board identity: key by what the board IS, never by which slot it lands in.** A component keyed on a nullable identifier (`key={slug ?? 'board'}`) silently collapses every instance onto one shared viewport state. In Chat view with multiple embedded boards, every board scrolled/zoomed in lockstep because `ExcalidrawPreview` was using a constant fallback key when `boardKey` wasn't passed. Fix: `boardInstanceKey(identity)` — returns identity when truthy, else mints a stable unique fallback (`__fallback-N__`, N increments per call). `ExcalidrawPreview` uses `key={boardInstanceKey(boardKey ?? slug)}`, so each board's pan/zoom is independent. This is the same class as other React-key footguns already documented (the pattern exists but wasn't applied here).
- **[2026-07-25] Phase-stamped UI overrides prevent both failure modes of sticky boolean state.** A user's collapse/expand override must be stamped with the phase it was made in, so it expires when the underlying run advances. A plain sticky boolean gets one failure mode whichever way you set it: (a) a user who collapsed a live group has it slam open again on the next frame (unstamped auto state winning), or (b) a user who merely re-opened a live group pins it open through the finish and never gets the auto-collapse this exists for. Stamping means: while the phase holds, the user's choice is the answer and no re-render may touch it; when the group actually crosses running → done (or a new run starts in a landed group), the stale choice is released and the automatic transition fires exactly once. `useGroupCollapse` binds this to component-local state, so the collapsed/open flag is per-card and per-group by construction — it lives in the instance, and ChatPane is keyed by session id, so it can leak neither across a split's panes nor across conversations.
- **[2026-07-25] Sub-agent work can survive its dead spawner — review the tree, don't re-dispatch.** Three dispatched sub-agents died when their spawning process closed, yet their work was still present in the working tree (two finished, one half-done). The correct recovery move was to review the uncommitted tree and finish the incomplete work directly, not to re-dispatch the same agents. Sub-agents are task-isolated, so a dead process doesn't corrupt the output — what's on disk is what was done.

- **[2026-07-26] One story per release, video-capable.** Announcements carry `story` (not `board`), one per version (never multiple stories for one release). Story schema supports `video` in hero and shot blocks (mp4/webm with poster + fallback), so a release can show motion (the roadmap-explainer proof reel ran Playwright against the dashboard to capture real UI in action). All shot kinds gain video support; a shot without `alt` is dropped (the screenshot IS the content).
- **[2026-07-29] A queue that only drains at the busy→idle edge is not the terminal's queue — the CLI steers, and the client was the thing holding it back.** Owner report three days after shipping the queue: *"normalde ilk boşlukta mesaj gönderirdi… ancak mesaj sonunda gidiyor."* Measured against real CLI 2.1.220 through this route's own stdin: a `user` frame written MID-TURN is delivered at the very next tool boundary, in the SAME turn (`num_turns: 2`, one `result`), and two frames written a second apart both arrive at that one boundary together. So "first opening" delivery had been free the whole time; `maybeFlushQueue` gating on `busy === false` was the entire latency. On a long turn that is a ten-second correction versus a five-minute one.
  - **The fix is two gestures, not a better queue.** ⏎/↑ steer into the running turn; ⇡ holds for the next one. The editable strip was a real feature (the owner had asked for it), and it only exists because the message is held client-side — so making ⏎ steer would have quietly deleted it. Keeping both, plus a per-row **Send now**, is what the owner actually asked for: *"ikisi de dursun ama anında gönder tuşu da olsun."*
  - **A steered message's transcript position runs ahead of the truth**, so it is labelled *sent mid-turn*: it renders the instant it goes on the wire, while the CLI only folds it in at the next boundary — the tool cards below it were decided before it was read. Without the label that gap reads as the agent ignoring you.
  - **⏎ must never silently degrade.** When a permission card is open, steering is refused (the card's own deny-with-a-message is the right affordance) — but parking the row as an ordinary queue entry would put the message right back at end-of-turn, i.e. the bug. So the fallback row is flagged `steerWhenPossible` and `maybeFlushQueue` steers it the moment there is an opening. `nextAutoSteer` respects `paused` where `canSteer` deliberately does not: an auto-drain must not outlive Stop, a hand on a button may.
  - **Two "Send now"s a few pixels apart, meaning different things, is worth a word.** The strip header's became **Resume** (lift the Stop pause, let the queue drain again); *Send now* now belongs to a row and means exactly one message.
- **[2026-07-26] Message queue pauses on Stop, never fires on interrupt.** An interrupt's own `result` frame is a busy→idle edge like any other. Fixed in two halves, both in `src/lib/claude-path.ts`: (1) `claudeAwarePath()` APPENDS the discovered install dir to the PATH of every spawn we own (terminal PTY, chat, sleepy chat/capture, tab titling, hook recall) — appended, never prepended, so a `claude` the user's rc already resolves is never redirected; (2) `ensureClaudeOnShellPath()` performs the missing echo into the user's rc (zsh → `~/.zshrc`, bash → `~/.bashrc` + `~/.bash_profile` only if it exists, fish → `config.fish` with `set -gx`, else `~/.profile`), idempotently under a `# dreamcontext:` marker, automatically after a successful `claude` install and on demand via the new `claude-path` installer target. Capabilities gained `claudePathBroken` (on disk, invisible to the shell) so Settings → System shows "Installed, not on your PATH" + a Fix PATH button instead of a false "Missing"; `claudeCli` now counts a discovered binary as present, because our spawns really can run it.
- **[2026-06-29] Prerequisite installer targets are a CLOSED whitelist.** `claude`, `claude-path`, `pty`, `git`; any other value → 400. Desktop-gated AND loopback-only. Package names are internal literals, never user input (no injection).
- **[2026-06-29] node-pty installed into CLI package root.** Walking up from `process.argv[1]` to find the nearest `package.json` ensures `import('node-pty')` resolves correctly from the bundled dist. Installing globally would not be visible to the server's module resolution.
- **[2026-06-29] Capabilities probed via -ilc (interactive login shell).** `claude` is commonly added to PATH in `~/.zshrc` (e.g. `~/.local/bin`), which a non-interactive `-lc` shell does NOT source. Using `-ilc` for the probe matches the PTY spawn exactly so detection can never disagree with the real spawn.
- **[2026-06-28] bypassPermissions opt-in, default OFF.** The terminal runs real `claude` with full file-write capability. The bypass is powerful and must be explicitly armed by the user.

Both are things the CLI's own readline gives the TERMINAL surface for free, which meant the surface that is now the DEFAULT was worse than the fallback at the two things you do constantly: lining up the next instruction mid-turn, and re-running something you already typed.
- **Root cause:** `Composer.submit()` opened with `if (busy || …) return` — ⏎ during a turn was a literal no-op, and the typed text just sat there. Nothing anywhere held a queue, and no history cursor existed on either surface's chat path.
- **Queue.** ⏎ while busy now routes to `session.enqueue`. The queue lives on the CONVERSATION MODEL (`ConversationModel.queued`), not in the composer: it has to survive minimize/restore and a re-home the way the draft does, and it has to drain where the busy edge is actually observed. Rows dock as a strip above the composer (`chat/QueuedMessages.tsx`, the `BackgroundShellsTray` precedent — pending input belongs beside the composer, not in the transcript, and must not scroll away), numbered, each editable in place (⏎ saves, ⇧⏎ newlines, Esc cancels — `stopPropagation`, or cancelling an edit would collapse the whole overlay — and saving an empty row deletes it) and removable, with Clear for the lot. They drain ONE PER TURN in order: each queued message is its own instruction and deserves its own turn, and one-per-turn is what makes the strip's ordering mean anything.
- **Two rules that are the whole point:** (1) **Stop pauses the queue.** An interrupt's own `result` frame is a busy→idle edge like any other, so without a pause flag, pressing Stop would fire the next queued message in the same breath as the interrupt — the user's own words, sent as the visible consequence of asking everything to stop. Paused, the strip says so and offers *Send now* / *Clear*; nothing is destroyed and nothing goes out unasked. (2) **A dead session keeps its rows.** `exited`/`authRequired` block the drain, and `QueuedMessages` is rendered OUTSIDE `ChatPane`'s composer/banner branch, so an ended session still shows the text — those rows are the only copy of it.
- **History.** ↑/↓ walk `promptHistory(conv.history, conv.items)` — newest first, consecutive duplicates collapsed, and covering a RESUMED conversation's replayed transcript, since re-running an earlier turn is half the point of resuming. It never eats a draft in progress: with non-empty text ↑ only recalls from caret 0 with nothing selected, ↓ is a history key only mid-walk, stepping forward past the newest restores the displaced draft verbatim, any keystroke ends the walk, and the slash menu keeps ↑/↓ while open. A recalled prompt starting with `/` deliberately does NOT open the command menu — `setSelectionRange` fires `onSelect`, so the suppression is state-based (`navRef`), not a one-shot at the recall site; otherwise ⏎ would COMPLETE the command instead of re-sending the prompt, which is the one thing the recall was for.
- **Glyphs:** the strip uses `◷` / `‖` and the queue button a dashed `⇡`, not ⏳/⏸/⏱ — this surface carries no colour emoji, and an amber hourglass reads as a warning rather than as "waiting its turn".
- **Runtime-verified** (verify skill, isolated scratch vault + fake HOME, a scripted stand-in for the CLI on PATH so turn timing was deterministic and no tokens were spent): 32 assertions green in BOTH themes against the real server and the real chat WS route — queue-on-⏎, edit/Esc-cancel/empty-deletes, one-per-turn drain in order, Stop pauses + the held message is provably not sent, Send now resumes, and every history rule including "↑ mid-draft does not recall" and "↓ past the newest restores the stash verbatim".
- Validation: 33 new unit tests (`tests/unit/chat-queue.test.ts` 21 + 12 history cases in `chat-entities.test.ts`, 162 total there), full suite 4638 passed / 0 failed, both `tsc` clean, `npm run build` clean.

### 2026-07-25 — The shells tray stopped eating the chat, and a "pinned" transcript now proves it is at the bottom
- **Owner report** (screenshots): after a long session the background-shells tray had grown into a wall of ~44 finished rows — "so many background jobs, it can't be scrolled, I can't see the chat, and I can't collapse it either" (the tray's own header had been pushed off with the transcript). Second report: "while the background-agent pin is up, the scroll goes too far down; an update fixes it, then it slides down again".
- **Root cause 1 — docked furniture had no ceiling.** The tray is deliberately OUTSIDE the scroller (a background shell outlives its turn), which means every row it holds is height the transcript does not get and cannot scroll past. Finished shells were kept "until the conversation ends", so the strip grew without bound and buried the transcript, its own collapse header and the composer. Fix: a finished row is evicted `FINISHED_SHELL_TTL_MS` (2 min) after it ends (`isShellVisible`, applied inside `summarizeBackgroundShells`), and the rows list scrolls inside `max-height: min(240px, 32vh)` instead of growing the tray. The tray wakes once at `nextExpiryAt` (the soonest row to expire) rather than polling — and `nextExpiryAt` is deliberately never derived from `now`, because the component schedules its next render FROM it (a `now`-derived value is a render loop). A shell's output is worth a seat while it runs and for the moment after; past that the command's own tool card in the transcript is the durable record.
- **Root cause 2 — a pinned view can be nowhere near the bottom, with nothing to notice it by.** Measured in Chromium (Playwright, real CSS): when docked furniture GROWS, the scroller shrinks under a view already at its maximum — `scrollTop` stays perfectly valid, the maximum moves out from under it, and **no scroll event is dispatched because nothing scrolled**. A tray growing 186px left 174px of transcript below the fold while the view still believed it was pinned, so no "↓ Latest" pill appeared either and the only thing that ever fixed it was the next frame of content arriving. Fix: `scrollToBottom` re-measures on the next `requestAnimationFrame` (`isAtBottom`, extracted so the pin and `nextStickToBottom` rule 1 share ONE definition) and re-pins if the bottom moved. Also: the `ResizeObserver` no longer re-subscribes on `syncRail`'s identity (which follows `subAgentCardEl`, so a fan-out's card mounting tore the observer down and back up) — that teardown window was the one gap where such a height change went unseen.
- **Measure, don't reason, about layout:** the mechanism was found by rebuilding the pane's real flex column + real CSS in a headless Chromium and probing `scrollTop`/`scrollHeight`/`clientHeight` before and after growing the tray — two minutes of probing replaced a long chain of plausible-but-wrong hypotheses (smooth scrolling, padding-bottom in flex scrollers, scroll anchoring). Same probe then verified the cap: 44 rows → tray 271px, header and composer both on screen, rows scrolling internally.
- Validation: 12 new unit tests (eviction window, every terminal status, stamp-less run keeps its row, `nextExpiryAt` soonest/absent/stable, `isAtBottom` incl. the silent-unpin case and agreement with `nextStickToBottom`). Both `tsc` clean.
