## Why

Developers using the dreamcontext desktop app need to run Claude Code interactively without leaving the app or opening a separate terminal window. The in-app Agent terminal embeds a full Claude Code TUI session directly in the Sleepy/Agent screen — full session parity (slash menu, skills, sub-agents, reasoning effort, real permission prompts) because it IS the client. In-app prerequisite detection and installation (node-pty, claude CLI) eliminate setup friction so the feature works out of the box.

As of 0.22 the TUI is no longer what you land in. The native **Chat** screen — the same engine rendered as app UI — is the default surface for every user, and the embedded terminal is kept as **Terminal (legacy)** behind Settings → Agents → "Agent screen". The flip includes a one-time migration: every pre-0.22 `agent-ui.json` carries `chatView:false` from the old opt-in default, so that value is only honoured once the blob has been stamped `screenMigrated` — which is what moves existing users onto Chat without overriding anyone who deliberately picks the terminal afterwards.

## User Stories

- [x] As a developer, I can run Claude Code in an embedded terminal inside the dreamcontext desktop app so I do not need a separate terminal window.
- [x] As a developer, I can navigate away from the Agent tab and return without losing my Claude Code session.
- [x] As a developer, I can opt into bypassing Claude Code's permission prompts so I can let it operate autonomously (with a standing warning shown while armed).
- [x] As a developer, I can split the view into side-by-side agent sessions to run parallel tasks.
- [x] As a developer, I can read Claude Code's output clearly in both light and dark themes without eyestrain or same-luminance-on-same-luminance blocks.
- [x] As a developer, I can install missing prerequisites (Claude CLI, node-pty) from within the app with one click so I never need to open a terminal just to unblock the Agent screen.
- [x] As a developer, I can access the agent terminal from any page via a global bottom-right FAB so I never need to navigate to a dedicated Sleepy page.
- [x] As a developer, I can see per-pane tab bars so it is always unambiguous which tab controls which pane.
- [x] As a developer, I can minimize an agent session to a corner dock chip and restore it as a new pane by clicking the chip, without losing state.
- [x] As a developer, I can use ⌘K to search the project brain (knowledge, features, tasks) from anywhere and navigate directly to a result.
- [x] As a developer, sessions I reopen correctly receive `--resume` only when a prior transcript exists, avoiding "No conversation found" errors on freshly created tabs.
- [x] As a developer, I can copy text out of the terminal — including non-ASCII characters — without a mangled clipboard or a jarring macOS beep.
- [x] As a developer, I can drop any file (not just images) onto the pane under my cursor and have its path handed to that session.
- [x] As a developer, I can converse with Claude in a native Chat view that renders tool calls, diffs, sub-agents, and inline media without a TUI layer.
- [ ] As a developer, I can use a read-only plan mode that shows Claude's intent without allowing file writes (external-terminal fallback offers it; in-app embedded plan mode pending).
- [x] As a developer, I can open a plain terminal tab (no Claude agent) scoped to the vault root alongside my agent tabs, so I can run shell commands without leaving the Agent surface.
- [x] As a developer, a new session's tab is auto-titled from my first message (via a cheap one-shot Haiku call), so I don't have to manually rename "Agent 1"/"Agent 2" tabs to tell them apart.
- [x] As a developer, I can toggle the whole Agents (beta) surface on/off, toggle tab-restore-on-launch, toggle auto-title, and set a custom in-app hotkey to open/close the Agents overlay, from Settings → Agents, so the surface fits how I actually work.
- [x] As a developer, when I open a task's in-pane agent session (Task Manager), the session boots idle with the pin prompt deferred to my first message, so I can type my question immediately instead of waiting for an auto-submitted prompt to complete.
- [x] As a developer, I can converse with Claude in a native Chat view that renders boards inline, plays media in place, makes file paths clickable, and shows action buttons — not just a terminal transcript — so I stay in one surface instead of jumping to search/preview for every artifact Claude makes.
- [x] As a developer, the Chat view lets me sign in to Claude directly from an auth-required banner that opens a shell tab with the correct login command, so I never hit a "run /login" dead-end in the headless surface.
- [x] As a developer, goal-skill and council live panels render above the Chat transcript (not just the terminal), so orchestrated runs show the same progress no matter which surface I picked.
- [x] As a developer, the Chat view shows a working indicator (dots + elapsed clock) before the CLI's first frame and in every gap between tool results, so "nothing on screen yet" reads as "working" rather than "stuck".
- [x] As a developer, auto-scroll in Chat sticks to the bottom through content-height changes (image loads, composer resize, split/move), not just new messages, so the answer stays in view instead of mysteriously scrolling off mid-turn.
- [x] As a developer, the Chat composer stays single-row at every pane width via a stage-driven context/usage readout (full → % only → bare bar → portaled card), so Send is always in the card and the toolbar never wraps.
- [x] As a developer, the Chat slash menu and skill picker match the terminal's (shared SkillPickerPopover), so I discover commands the same way in both surfaces instead of having to remember syntax.
- [x] As a developer, tool cards in Chat collapse by default (except Edit/Write, which open automatically), so I see what changed in my files without scrolling past hundreds of lines of shell output.
- [x] As a developer, I can switch Settings → Agents → "Agent screen" between Chat (the default) and Terminal (legacy), so the surface fits how I work — and already-running sessions keep their surface while new ones follow the setting.
- [x] As a developer upgrading from an older version, my next launch opens Chat even though I never enabled the beta — the one-time move happens once, and if I deliberately pick Terminal (legacy) afterwards it sticks.

- [x] Session persists via `display:none` hoist of `AgentSurface` above `App.tsx` page switch; torn down only on explicit Close/Restart or app quit.
- [x] Renderer is user-selectable (2026-07-23, supersedes the 2026-07-01 DOM-only AC): `renderer: 'webgl' | 'dom'` in AgentSettings, default `webgl` (Smooth — GPU frame rate under heavy streams); `dom` (Comfort) keeps real text nodes with native macOS anti-aliasing (`.xterm { -webkit-font-smoothing: auto }` overrides the app-wide reset's forced `antialiased`). Applies LIVE to open sessions via `AGENT_SETTINGS_EVENT`; WebGL `onContextLoss` → dispose + DOM fallback.

## Constraints & Decisions
<!-- LIFO: newest decision at top -->

- **[2026-07-25] Excalidraw pinch zoom is module-level state — per-instance registration required.** `@excalidraw/excalidraw` 0.18 drives WebKit pinch gestures from module-level state shared by every `<Excalidraw>` instance on the page, so one board's pinch was zooming ALL boards to the same level. `excalidrawPinch.ts` `registerPinchTarget()` / `unregisterPinchTarget()` per-instance fix: each canvas calls register after `excalidrawAPI` mounts (lazy, because the API arrives in an effect) and unregister on unmount. The API is read lazily, never assumed present.
- **[2026-07-25] Composer drag sets a FLOOR, never a fixed height.** Both drag and auto-grow want to own the composer's height, so one must be subordinate. Rule: `applied = min(ceiling, max(autoGrown, draggedFloor))`. Auto-grow is what the CONTENT needs (may always push up to ceiling). Drag is what the USER asked for (a minimum the content may exceed but never undercut — a deliberately tall box doesn't collapse under you when you send or delete a line). Neither may pass paneHeight/2 (the ceiling drag has always enforced — auto-grow can't reach a size drag is forbidden). Visible consequence: dragging DOWN stops at the current draft's natural height (won't hide typed text). With a short draft (common case), the full drag range is available because the natural height IS the two-line minimum. After send the draft is empty, so autoGrown collapses to 2-line min and box returns to max(min, draggedFloor) — i.e. to two lines for anyone who never touched the handle, to their chosen size for anyone who did. Drag is a standing choice, not leftover state.
- **[2026-07-25] Per-instance board identity: key by what the board IS, never by which slot it lands in.** A component keyed on a nullable identifier (`key={slug ?? 'board'}`) silently collapses every instance onto one shared viewport state. In Chat view with multiple embedded boards, every board scrolled/zoomed in lockstep because `ExcalidrawPreview` was using a constant fallback key when `boardKey` wasn't passed. Fix: `boardInstanceKey(identity)` — returns identity when truthy, else mints a stable unique fallback (`__fallback-N__`, N increments per call). `ExcalidrawPreview` uses `key={boardInstanceKey(boardKey ?? slug)}`, so each board's pan/zoom is independent. This is the same class as other React-key footguns already documented (the pattern exists but wasn't applied here).
- **[2026-07-25] Phase-stamped UI overrides prevent both failure modes of sticky boolean state.** A user's collapse/expand override must be stamped with the phase it was made in, so it expires when the underlying run advances. A plain sticky boolean gets one failure mode whichever way you set it: (a) a user who collapsed a live group has it slam open again on the next frame (unstamped auto state winning), or (b) a user who merely re-opened a live group pins it open through the finish and never gets the auto-collapse this exists for. Stamping means: while the phase holds, the user's choice is the answer and no re-render may touch it; when the group actually crosses running → done (or a new run starts in a landed group), the stale choice is released and the automatic transition fires exactly once. `useGroupCollapse` binds this to component-local state, so the collapsed/open flag is per-card and per-group by construction — it lives in the instance, and ChatPane is keyed by session id, so it can leak neither across a split's panes nor across conversations.
- **[2026-07-25] Sub-agent work can survive its dead spawner — review the tree, don't re-dispatch.** Three dispatched sub-agents died when their spawning process closed, yet their work was still present in the working tree (two finished, one half-done). The correct recovery move was to review the uncommitted tree and finish the incomplete work directly, not to re-dispatch the same agents. Sub-agents are task-isolated, so a dead process doesn't corrupt the output — what's on disk is what was done.

- **[2026-07-25] `parent_tool_use_id` is on the FRAME, never on the content block — and a sub-agent's tool calls are DROPPED from the parent transcript, not rendered.** Spiked on CLI 2.1.220 (a real Agent dispatch, every frame dumped): a sub-agent's own tool calls ARE streamed to the parent as ordinary `assistant` tool_use / `user` tool_result frames, each stamped with a top-level `parent_tool_use_id`, while `content[0].parent_tool_use_id` is absent. `chatProtocol` read only the block, so `ChatToolItem.parentToolUseId` was always undefined and the sole suppression in ChatPane (`subAgentToolUseIds`) covers just the spawning `Agent` call — so with 3 sub-agents running, the main transcript filled with Read/Bash cards the main agent never ran, with nothing attributing them to anyone. That inverts the reason to dispatch isolated agents: the parent view says WHICH runs are live and what each is doing (`task_progress.activity`), and the step-by-step lives behind the drill-in. Note `usageOf` had always read the frame correctly — the two disagreeing about where the field lives was the tell. New `frameParent()` is the single gate; four rules follow from it. (a) A sidechain `stream_event` is dropped WHOLE, not attributed: block `index` is per-message, so a sub-agent's block 0 and the parent's block 0 would collide in the reducer's `openBlocksByIndex` and splice a sub-agent's deltas into the parent's own bubble (the CLI does not stream sidechain partials today — this keeps that from becoming a corruption bug the day it does). (b) `tool-result` carries the attribution too, and the reducer skips its ENTIRE card block for a parented one — load-bearing, because that arm MATERIALIZES a card for an unknown `tool_use_id`, so suppressing only the tool_use would have turned every sub-agent result into a nameless card holding its raw output: a worse leak than the original. (c) The parent's own final Agent-call result carries NO `parent_tool_use_id` (verified), which is what makes gating on it safe. (d) `ChatToolItem.parentToolUseId` is DELETED rather than left unread — a field that looks like attribution but is never populated is precisely what made this bug invisible for a month.
- **[2026-07-25] The transcript-history parser needs to know WHICH transcript it is reading.** `isSidechain` means opposite things in the two files `parseTranscriptHistory` serves: in a parent transcript it marks another agent's turns (drop them, or a resume replays the leak above — older CLIs inlined sidechain turns; 2.1.220 keeps them in `<uuid>/subagents/agent-<taskId>.jsonl`), while in a sub-agent's own file EVERY entry carries it and dropping them empties the drill-in. Hence `opts.sidechain`, passed true only by the `?subagent=` route. Caught by an existing test going red — the reason that test exists.

- **[2026-07-25] Background shells are read and killed OUT-OF-BAND, never through the model.** A `run_in_background` Bash was invisible in Chat, and the obvious fix (ask the agent to run `TaskOutput`/`TaskStop`) costs a turn, can't run while the conversation is busy, and puts a UI affordance behind a model decision. A spike of CLI 2.1.220 found two better channels, both verified: (1) the CLI streams a backgrounded command's output to a FILE (`/tmp/claude-<uid>/<realpath(cwd) slug>/<sessionUuid>/tasks/<taskId>.output`), so the server reads it directly — new `GET /api/agent/bg-output`, path fully server-derived, task id gated to `^[a-z0-9]{1,32}$` (no dot/slash/dash, so traversal is unrepresentable), 256KB tail, and the stream's own `output_file` never trusted; (2) `control_request{subtype:'stop_task', task_id}` kills it — no tokens, no turn. Two path details are pinned because they are easy to get wrong: the base is a HARDCODED `/tmp/claude-<uid>`, NOT `$TMPDIR`/`os.tmpdir()` (verified by pointing TMPDIR elsewhere — other temp files moved, these did not; macOS sets a custom TMPDIR by default, so a tmpdir()-derived path would have found nothing), and the cwd segment slugs the REALPATH of cwd.
- **[2026-07-25] `stop_task`'s ack is not evidence — the roster frames are.** The CLI answers `{subtype:'success', response:{}}` even for a task id that never existed (verified with a bogus id), so neither the server nor the client treats the ack as confirmation and nothing is marked stopped locally on the strength of having asked. The truthful signals are `system:background_tasks_changed` + `task_updated{status:'killed'}`, which the reducer applies. For the same reason the `background_tasks` LIST control request is unused: it acks success and returns an empty `{}` (with or without `include_output`), so the roster can only come from the push.
- **[2026-07-25] The roster push is a RECONCILER, not the list.** `system:background_tasks_changed` carries only tasks STILL RUNNING — a finished one simply drops out. So it is used to adopt a shell whose `task_started` we missed and to close out one that vanished without a terminal frame, never to replace the tray's list: doing that would delete every finished shell and its still-readable output the instant it ended.
- **[2026-07-25] Background shells get their own surface; they are not sub-agents.** Both ride the identical `system:task_*` frames, discriminated ONLY by `task_type:'local_bash'` — which caused two real bugs. (1) `subAgentToolUseIds` suppressed the spawning tool card, but for a shell that id is the `Bash` call itself, so backgrounding a command ERASED its card and the user never saw what was running; it now filters to agent runs. (2) Clicking a shell row drilled into a sidechain transcript that does not exist for a shell, showing a misleading "hasn't flushed yet" about a file that was never going to appear. The split is by affordance, not taxonomy: an agent run has a transcript to read and no lifecycle the user controls; a shell has no transcript but has live output and a stop button. `SubAgentCard` now filters internally so no caller can reintroduce the mix.
- **[2026-07-25] `stopped` is its own terminal status.** `stop_task` produces `task_updated{status:'killed'}` then `task_notification{status:'stopped'}`; both fell through the reducer's `completed`/`error` ternary to `cur.status`, so a killed run displayed as "running" forever. Shared pure `runStatusFrom(raw, current)` now maps the CLI's whole vocabulary, holds the current status for an unrecognized word (a future status must not silently retire a running row), and stamps `endedAt` when a frame omits it. Calling a user-killed run "completed" or "failed" would misreport it, so it is neither.

- **[2026-07-23] Status chip is hook-driven, not stream-driven.** The busy/ready split used to be guessed from PTY stream activity + a screen-tail regex (`WORKING_RE`), which read every quiet gap the regex missed as "ready" while Claude was still mid-turn — the #1 status complaint. Ground truth is the turn lifecycle the hooks already observe: the server exports `DREAMCONTEXT_AGENT_STATUS_FILE` into the PTY env (same inheritance as `DREAMCONTEXT_DEFERRED_PROMPT`), `hook user-prompt-submit` writes `working` and `hook stop` writes `ready` (`writeAgentTurnState` — atomic tmp+rename so the watcher never reads a torn file; basename-prefix guard against hostile env; `isNestedClaudeHook()` guard so a `claude -p` run via Bash can't flip the outer tab), the server watches the file and relays transitions as BINARY WS frames (output is always text frames — the channels can't collide, and old clients ignore binary). Client rules: once a frame arrives the hook owns busy/ready; `asking` stays with the screen regex (permission prompts fire no hook); Esc/Ctrl+C suspends hook authority until the next hook event (Claude Code fires NO Stop on user interrupts); hook-less vaults / older CLIs never write the file, so the old heuristic remains the silent fallback.

- **[2026-07-23] Transport perf: coalescing pump + client-acked flow control; renderer deliberately untouched.** The PTY→WS path forwarded every node-pty chunk as its own WS frame (Claude's Ink TUI emits hundreds of tiny chunks/sec while streaming), and nothing bounded xterm's write buffer when a burst outran the DOM renderer — the two transport causes of terminal stutter/freezes. Fix lives in `createOutputPump()` (agent-terminal.ts, exported + unit-tested): coalesce chunks in a 5ms window (64KB early-flush) into one frame; client acks processed chars every 32KB via xterm's write callback (both sides count JS string length, so the metric can't drift); server pauses the PTY above 512KB un-acked and resumes at ≤128KB. Pausing arms ONLY after the client's n=0 hello ack (sent on socket open) — a client that never acks keeps fire-and-forget instead of stalling the PTY forever. Safe for hidden/parked panes: xterm processes writes (and fires callbacks) in its common core, independent of `open()`; dormant restored tabs have no WS at all. Remaining steady-state render cost is a renderer question, not transport — addressed the same day by the renderer setting below.
- **[2026-07-23] Renderer is a setting: WebGL (Smooth) default, DOM (Comfort) opt-in — supersedes the 2026-07-01 DOM-only decision.** The 2026-07-01 "DOM renderer over WebGL" call was justified as an acceptable trade "for a low-throughput viewport"; Claude's Ink TUI redrawing most of the viewport every frame while streaming falsified that premise (user-reported stutter, "Zed kadar akıcı olmalı"). New `renderer: 'webgl' | 'dom'` in AgentSettings (Settings → Agents → Terminal rendering; persisted in `~/.dreamcontext/agent-ui.json`, coerced server+client): default `webgl` loads `@xterm/addon-webgl` after `term.open()`; `dom` keeps the native-text comfort path. Swappable LIVE on open sessions (agentSession listens for `AGENT_SETTINGS_EVENT`; loading the addon upgrades in place, disposing drops xterm back to the DOM renderer) so the user can A/B glyph feel instantly. `onContextLoss` disposes the addon and falls back to DOM (WKWebView reclaims GPU contexts under pressure; many panes can also exhaust the per-page context cap — fallback, never a dead canvas).
- **[2026-07-23] Two permission modes only: Auto (acceptEdits) replaces plain manual as the no-bypass default.** Owner decision ("if no bypass that means it is auto — never manual"): an agent spawn is either `--permission-mode bypassPermissions` (bypass armed; unchanged semantics, warning chip) or `--permission-mode acceptEdits` (file edits auto-approved, commands/tools still prompt). Applied in `startPtySession` AND the external `open-terminal` fallback. The corner `BypassPill` is now a two-state mode indicator: calm accent "auto" ⇄ orange "bypass" — the mode is always visible, not just the dangerous half. The `bypass` boolean stays the single wire/roster field; no tri-state threading.
- **[2026-07-17] Terminal slot contract — position:relative, agent-pane-slot class, resize observation, container query.** Any DOM slot receiving the agent terminal's container must: (a) be `position:relative` (container is `absolute inset:0` — without it the terminal resolves to the nearest positioned ancestor, e.g. a fixed overlay = whole-page takeover); (b) carry the `agent-pane-slot` CLASS (all xterm visual rules — 14/20px padding, transparent viewport, scrollbar skin, letter-spacing measurement fix — are scoped to it) but NOT `data-pane` (the surface's pane-homing query); (c) sit on `--color-bg` canvas; (d) be observed for resize (the overlay's ResizeObserver only watches `hostRef` — page-tree slots need their own, 150ms settle debounce) or the xterm grid goes stale and clips; (e) declare `container: agentpane / inline-size` if it hosts the composer, or the `@container` breakpoints never match.
- **[2026-07-17] Portal composer pattern for in-pane sessions (Task Manager).** The per-pane composer bar (`PaneComposer`) is reused OUTSIDE the overlay by React-portaling it from `AgentSurface` into a page-owned anchor div (`.agent-task-manager-composer[data-task]`) — the React-rendered counterpart of the raw-DOM terminal hoist. Rule: composer actions need surface-owned session state, so the surface renders the portal; TM sessions are roster-less by design, so TM action helpers resolve straight from the live sessions map and never `setExpanded`.
- **[2026-07-17] Deferred first-message context (deferPrompt).** A new cross-layer mechanism: the embedded terminal can park an initial prompt instead of auto-submitting it. Client: `deferPrompt` param through `createSession`/spawn → `&deferPrompt=1` on the WS upgrade. - **[2026-07-10] WKWebView clipboard is persistently hostile to UTF-8 — third fix, Tauri native clipboard is durable.** Copying Turkish/UTF-8 text from the terminal regressed AGAIN (Ş→"≈û", ü→"√º"), despite the 2026-07-01 `execCommand('copy')` fix. Setting `minimumContrastRatio: 1` "to keep the exact palette" causes unreadable block fills in both themes. ### 2026-07-25 — The shells tray stopped eating the chat, and a "pinned" transcript now proves it is at the bottom
- **Owner report** (screenshots): after a long session the background-shells tray had grown into a wall of ~44 finished rows — "so many background jobs, it can't be scrolled, I can't see the chat, and I can't collapse it either" (the tray's own header had been pushed off with the transcript). Second report: "while the background-agent pin is up, the scroll goes too far down; an update fixes it, then it slides down again".
- **Root cause 1 — docked furniture had no ceiling.** The tray is deliberately OUTSIDE the scroller (a background shell outlives its turn), which means every row it holds is height the transcript does not get and cannot scroll past. Finished shells were kept "until the conversation ends", so the strip grew without bound and buried the transcript, its own collapse header and the composer. Fix: a finished row is evicted `FINISHED_SHELL_TTL_MS` (2 min) after it ends (`isShellVisible`, applied inside `summarizeBackgroundShells`), and the rows list scrolls inside `max-height: min(240px, 32vh)` instead of growing the tray. The tray wakes once at `nextExpiryAt` (the soonest row to expire) rather than polling — and `nextExpiryAt` is deliberately never derived from `now`, because the component schedules its next render FROM it (a `now`-derived value is a render loop). A shell's output is worth a seat while it runs and for the moment after; past that the command's own tool card in the transcript is the durable record.
- **Root cause 2 — a pinned view can be nowhere near the bottom, with nothing to notice it by.** Measured in Chromium (Playwright, real CSS): when docked furniture GROWS, the scroller shrinks under a view already at its maximum — `scrollTop` stays perfectly valid, the maximum moves out from under it, and **no scroll event is dispatched because nothing scrolled**. A tray growing 186px left 174px of transcript below the fold while the view still believed it was pinned, so no "↓ Latest" pill appeared either and the only thing that ever fixed it was the next frame of content arriving. Fix: `scrollToBottom` re-measures on the next `requestAnimationFrame` (`isAtBottom`, extracted so the pin and `nextStickToBottom` rule 1 share ONE definition) and re-pins if the bottom moved. Also: the `ResizeObserver` no longer re-subscribes on `syncRail`'s identity (which follows `subAgentCardEl`, so a fan-out's card mounting tore the observer down and back up) — that teardown window was the one gap where such a height change went unseen.
- **Measure, don't reason, about layout:** the mechanism was found by rebuilding the pane's real flex column + real CSS in a headless Chromium and probing `scrollTop`/`scrollHeight`/`clientHeight` before and after growing the tray — two minutes of probing replaced a long chain of plausible-but-wrong hypotheses (smooth scrolling, padding-bottom in flex scrollers, scroll anchoring). Same probe then verified the cap: 44 rows → tray 271px, header and composer both on screen, rows scrolling internally.
- Validation: 12 new unit tests (eviction window, every terminal status, stamp-less run keeps its row, `nextExpiryAt` soonest/absent/stable, `isAtBottom` incl. the silent-unpin case and agreement with `nextStickToBottom`). Both `tsc` clean.
