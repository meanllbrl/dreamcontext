# Neuroscience Mapping (Archived 2026-H2)

> Extracted from `core/6.system_flow.md` on 2026-08-10 to meet the ~4,000-char core file ceiling. This mapping reflects the original design inspiration (Joo & Frank 2025 Science paper on the brain's two-stage memory selection system).

## Design Rationale

Inspired by a 2025 Science paper (Joo & Frank) revealing the brain's two-stage memory selection system. The hippocampus records experiences AND fires "awake ripples" to bookmark important moments during the day. During sleep, bookmarked memories compete for consolidation, with only the strongest patterns winning transfer to the neocortex. Key insight: memory selection (tagging) and memory consolidation (storage) are separate processes.

## Data Flows (Archived Detail)

**Bookmark flow**: Agent calls `bookmark add` -> stored in .sleep.json bookmarks[] -> stop hook links to session -> sleep agent reads first -> consolidated into soul/user/memory/knowledge

**Knowledge decay flow**: Agent reads knowledge file -> calls `knowledge touch <slug>` -> .sleep.json knowledge_access updated -> snapshot shows staleness indicators + warm knowledge tier -> sleep agent uses access data for anti-bloat

**Trigger flow**: Sleep agent creates trigger -> stored in .sleep.json triggers[] -> snapshot matches against active tasks/tags/bookmarks -> matching triggers shown as contextual reminders -> fired_count incremented -> expired by sleep done when past max_fires

**Transcript distillation flow**: Sleep agent calls `transcript distill <session_id>` -> reads JSONL transcript -> auto-filters to content after `consolidated_at` if session was previously consolidated (prevents re-reading already-processed content) -> structural filter keeps user messages, thinking blocks, agent decisions, Write/Edit calls with byte deltas, Bash changes, errors, bookmarks, subagent I/O -> discards Read/Glob/Grep results, tool metadata, internal subagent tool calls -> outputs structured markdown. `--full` shows entire transcript; `--since <iso>` for manual cutoff.

## Context handoff — full mechanics (archived from `core/6.system_flow.md`, 2026-09-13)

**Context handoff (opt-in, default OFF)** rides the EXISTING hooks — deliberately no eighth `HOOK_SPECS` entry, because `npx dreamcontext` measures ~1.0s per hook call and an all-tools PostToolUse would add a second to every tool call. PostToolUse (every Edit/Write, not just JS/TS) and UserPromptSubmit carry the nudge past `nudgeAt`; SessionStart prints the `>> HANDOFF:` banner before the snapshot and sweeps `state/.context-watch/` + `state/.handoff-requests/`; PreCompact stamps `context_tokens` on its CompactionRecord. Resolution is per-pane tab file > `.config.json` `contextHandoff` > off; the nudge ladder is keyed by session (a `/clear` restarts it) while the toggle is keyed by pane (it survives). Never fires inside a sub-agent (`agent_id`/`agent_type` on the payload, verified against a real payload). Canonical: `src/lib/context-watch.ts`.

Measured (2026-09-13, 120 real sessions / 10,917 API calls): ~97.4% of billed input tokens are cache reads; a 200k-handoff strategy versus riding a 1M context differ by 2.2–2.6x input tokens. One live handoff measured 429,471 -> 105,462 tokens (4.07x, -75.4%) using the shipped `lastMainChainContext`.
