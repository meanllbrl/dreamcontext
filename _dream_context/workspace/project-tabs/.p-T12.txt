## 1. `chatPermissionMode` — SPLIT IT OUT OF THE GLOBAL BLOB (the dangerous one)
`agentSettings.ts:69` holds `chatPermissionMode: 'auto' | 'bypass'`, and its own doc comment
(`:64-68`) says `'bypass'` maps to `bypassPermissions`. `AgentSurface.tsx:425` reads it (via the
ref at `:250-251`) to set `effectiveBypass` for EVERY chat session that instance spawns. It
rides the app-global blob and propagates on `AGENT_SETTINGS_EVENT` on `window`.

Today that cannot cross projects because each vault is its own JS realm. In ONE realm, flipping
bypass while looking at project A silently rewrites project B's remembered default and every
session B spawns afterwards — agent auto-approval turned on in a project the user never
touched. Same class as `checklistStore.ts`'s header warning, applied to a permission gate.

In `agentSettings.ts`:
- REMOVE `chatPermissionMode` from `AgentSettings`, `DEFAULT_AGENT_SETTINGS`,
  `coerceAgentSettings` and the server mirror. Every OTHER field stays app-global on its
  existing path (`writeAgentSettings` → localStorage + `/launcher/agent-settings` +
  `AGENT_SETTINGS_EVENT` on `window`) — do not disturb that.
- ADD:
```ts
export type ChatPermissionMode = 'auto' | 'bypass';
export const CHAT_PERMISSION_MODE_KEY = 'agent:settings:chatPermissionMode';
export const CHAT_PERMISSION_MODE_EVENT = 'dc-chat-permission-mode';   // INSTANCE BUS, not window
export function readChatPermissionMode(vault: string | null): ChatPermissionMode;
export function writeChatPermissionMode(bus: EventTarget, vault: string | null, mode: ChatPermissionMode): void;
```
- `readChatPermissionMode` reads `readScopedRaw(vault, CHAT_PERMISSION_MODE_KEY)` and returns
  `'bypass'` ONLY on an exact `'bypass'` match; absent, stale or malformed → `'auto'`. This
  preserves the posture already documented at `:107-109` ("only an explicit 'bypass' opts into
  the caution mode").
- `writeChatPermissionMode` persists and then `emitInstance(bus, CHAT_PERMISSION_MODE_EVENT, mode)`.
- **MIGRATION: deliberately DROP the legacy value. No `keepLegacy`, no copy.** This is the one
  key where copying forward is the harm — a globally-set `'bypass'` would fan out to every
  project at once. Every vault starts at `'auto'` and the user re-opts-in per project. A
  one-time reset of a permission toggle is the correct trade; write that reasoning in a comment.

In `SettingsPage.tsx` (~:253): stop routing `chatPermissionMode` through `writeAgentSettings`.
The rest of the blob keeps its global path untouched.

**`AgentSurface.tsx` is NOT yours** — T11 (this wave, next batch) switches its reads and its

## 2. `autoCheckpointOnOpen` — SCOPE IT, and use `keepLegacy`
`brainSyncPrefs.ts` controls whether opening the dashboard auto-COMMITS uncommitted local edits.
That is real git behaviour and it belongs per-repo.
```ts
export function readAutoCheckpointOnOpen(vault: string | null): boolean;
export function writeAutoCheckpointOnOpen(vault: string | null, enabled: boolean): void;
```
**`keepLegacy: true` is MANDATORY here.** `:18-21` returns `getItem(KEY) !== '0'` — i.e. the
unset default is ON. Under the plain copy-once-then-delete policy, a user who deliberately
turned auto-checkpoint OFF would keep that intent for exactly ONE vault; every other vault would
find no scoped key, fall back to ON, and silently start auto-committing their work. The general
rule (already in `scopedStorage.ts`): copy-once-then-delete is only safe when the unset-fallback
is the SAFE direction. It is not, here.
`AUTO_CHECKPOINT_EVENT` is verified DEAD CODE — dispatched, zero `addEventListener` anywhere in
`dashboard/src`. Leave it exactly as it is; do not move it to a bus.
