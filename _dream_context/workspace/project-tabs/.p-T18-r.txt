## THE BUG
`ProjectRollup.live` deliberately excludes `kind === 'shell'` rows — correct, because `live` is
the chat BADGE count and a shell has no agent behind it. Your unit test pins that and it stays
pinned.

But the CEILING rule in `WindowChrome.tsx` also gates eviction on `rollup.live === 0`. So a
project whose only live thing is a running SHELL — a dev server, a build watch, an interactive
process the user is monitoring — reports `live: 0`, gets picked as "idle", is torn down into a
cold chip, and its PTY is killed mid-process. That is the exact class of failure this entire
design exists to prevent; it just escaped through `shell` instead of `agent`/`chat`.

I reused a badge count for a life-or-death decision. The fix is to stop conflating them.

## YOUR CHANGE — one new field, additive
`dashboard/src/components/sleepy/agentStatus.ts`:
```ts
export interface ProjectRollup {
  worst: SessionStatusKind;
  live: number;    // UNCHANGED — the badge count: chats/agents only, shells excluded
  waiting: number; // UNCHANGED
  /** Eviction safety: how many sessions of ANY kind still hold a live PTY/WebSocket —
   *  agent, chat AND shell. This is the ONLY field the ceiling rule may consult. `live` is a
   *  presentation count and must never decide whether an instance can be torn down. */
  alive: number;
}
```
- `alive` counts a row when `info.kind` is neither `'saved'` nor `'ended'` — **regardless of
  `kind`**, so shells are included. (`saved` is a restored roster row with no live session;
  `ended` is a dead PTY. Everything else holds something real.)
- `live` keeps its exact current definition. Do not touch it, and do not touch `worst` or
  `waiting`.
- Empty input → `{ worst: 'ended', live: 0, waiting: 0, alive: 0 }`.
- Put the "why two counts" reasoning in the interface comment. The next person to read this
  will otherwise assume one of them is redundant and delete it — which is precisely how this
  bug would come back.
