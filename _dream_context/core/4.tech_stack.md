## Tech Stack

TypeScript 5.7, Node.js >= 18, ESM-only npm package. CLI + local HTTP server + React SPA dashboard + Lab analytics-insights subsystem (v0.10.7+).

## Architecture Overview

Single-binary CLI tool that can also serve a local web dashboard. No external services. All state lives on the local filesystem in `_dream_context/` directories within user projects.

> Full source layout, build pipeline, and infrastructure details archived to `knowledge/archive/4.tech_stack-dependencies-2026-h2.md`.

## Dashboard Architecture Constraints

**Per-vault ApiClient pattern (v0.24.0+):** The dashboard's `api/client.ts` is now a **per-vault ApiClient class** (`constructor(private readonly vault: string…)`). The module-level singleton `api` import was retired across nearly all `dashboard/src/hooks/*`. Future dashboard code MUST use the ApiClient class, never a module-level singleton — hooks receive vault context from VaultContext and instantiate their client accordingly. This supports the one-window multi-vault (project tabs) feature.

**Never reuse display fields as safety/control predicates (2026-08-11):** A field intended for presentation must never be silently reused as a safety or control predicate. Two independent runtime defects (both missed by 6,944 green tests): (1) instance eviction reading the `live` badge counter (excludes shells) so a dev-server-only project looked idle and would be killed — fixed with separate `alive` counter for the safety gate; (2) `chatPanes` filtering on display `kind` so automation-run tabs spawned live-but-never-mounted sessions — one field double-booked between tab glyph and pane mount. Both caught only by runtime measurement. When a count/flag drives a decision (eviction, mounting, activation), give it its own field with a name that states its purpose.
